# Бенчмарк Cassandra для NeoHome

## Що це і навіщо

Бенчмарк — це **контрольований навантажувальний тест**. Ми штучно створюємо потік HTTP-запитів до API, імітуючи сотні IoT-пристроїв, що одночасно шлють дані. Мета — виміряти, скільки запитів Cassandra витримує за секунду і з якою затримкою.

Це не тест коректності (для цього є `back/test/e2e_api_test.sh`). Це тест **продуктивності** — "скільки ми витримаємо під навантаженням".

## Інструмент: autocannon

**autocannon** — це Node.js бібліотека для HTTP навантажувального тестування. Працює так: відкриває N TCP-з'єднань до сервера і безперервно шле запити протягом заданого часу, вимірюючи швидкість відповідей та затримки.

Ми використовуємо **програмний API** (не CLI), бо:
- потрібно динамічно генерувати тіло кожного запиту (унікальні timestamp'и, ротація пристроїв)
- потрібен етап підготовки даних (seed) перед тестом
- результати зберігаються в JSON для порівняння між запусками

## Як запустити

```bash
# Переконатися що сервіси запущені
docker compose up -d

# Встановити залежності та запустити всі 5 сценаріїв
cd bench && npm install
npm run bench

# Окремі сценарії:
npm run bench:write           # запис телеметрії
npm run bench:alerts          # запис з генерацією алертів
npm run bench:read            # читання історії
npm run bench:latest          # читання останніх показників
npm run bench:mixed           # мікс 80% запис / 20% читання

# Налаштування параметрів:
BENCH_DURATION=60 BENCH_CONNECTIONS=20 npm run bench
```

## Структура файлів

```
bench/
  package.json              ← npm-проєкт з залежністю autocannon
  config.js                 ← всі налаштування (URL, тривалість, кількість з'єднань)
  seed.js                   ← підготовка тестових даних через API
  run.js                    ← головний оркестратор: seed → warm-up → тест → звіт
  scenarios/
    write-telemetry.js      ← сценарій 1: запис телеметрії без алертів
    write-with-alerts.js    ← сценарій 2: запис з перевищенням порогів → алерти
    read-telemetry.js       ← сценарій 3: читання історії телеметрії
    read-latest.js          ← сценарій 4: читання останніх показників
    mixed-workload.js       ← сценарій 5: мікс 80% запис / 20% читання
  results/                  ← JSON-файли з результатами кожного запуску
  RESULTS.md                ← документовані результати з аналізом (англ.)
```

## Конфігурація (`config.js`)

| Параметр | За замовчуванням | Змінна середовища | Опис |
|----------|-----------------|-------------------|------|
| BASE_URL | `http://localhost:3434` | `BENCH_API_URL` | Адреса Go API |
| DURATION_SECONDS | 30 | `BENCH_DURATION` | Тривалість кожного сценарію |
| WARMUP_SECONDS | 5 | `BENCH_WARMUP` | Прогрів перед кожним сценарієм |
| CONNECTIONS | 10 | `BENCH_CONNECTIONS` | Кількість паралельних TCP-з'єднань |
| PIPELINING | 1 | `BENCH_PIPELINING` | Запитів "в польоті" на з'єднання |
| DEVICE_COUNT | 5 | `BENCH_DEVICES` | Кількість тестових пристроїв |

### Термінологія конфігурації

**Connections** — кількість одночасних TCP-з'єднань до сервера. 10 з'єднань = 10 "клієнтів", які паралельно шлють запити. Імітує 10 IoT-пристроїв або 10 користувачів.

**Pipelining** — HTTP pipelining: відправка наступного запиту **не чекаючи відповіді** на попередній. При `1` кожне з'єднання чекає відповіді перед наступним запитом (найреалістичніший режим). При `10` кожне з'єднання тримає 10 запитів "в польоті" одночасно — штучно збільшує throughput.

**Warm-up** — "прогрів": коротке навантаження (5 сек), результати якого **відкидаються**. Навіщо: JVM Cassandra компілює "гарячий" код (JIT-компіляція), Go встановлює connection pool, кеші заповнюються. Без прогріву перший сценарій показав би штучно високі затримки, бо система ще "холодна".

## Seed — підготовка тестових даних

Перед бенчмарком потрібні реальні дані в Cassandra, інакше всі запити повертатимуть 404. Seed робить це через API (не напряму в базу), щоб дані проходили ту саму валідацію, що й у продакшені.

**Кроки:**

1. **Реєстрація користувача** — `POST /api/v1/auth/register` з унікальним email (включає timestamp, щоб не конфліктувати з попередніми запусками)
2. **Логін** — `POST /api/v1/auth/login/email` → отримуємо JWT токен (потрібен для authenticated ендпоінтів)
3. **Створення 5 пристроїв** — `POST /api/v1/devices`, кожен у своїй локації (`locationId: 1..5`). Різні локації = різні партиції в Cassandra = реалістичний розподіл навантаження
4. **Встановлення порогів** — `PUT /api/v1/devices/{id}/thresholds`: temperature min=10, max=35. Потрібно для сценарію з алертами
5. **Наповнення телеметрії** — 50 рядків на кожен пристрій (250 всього), розкиданих по останній годині. Потрібно, щоб read-сценарії мали дані для читання

## 5 сценаріїв — що саме тестується

### 1. `write-telemetry` — Чистий запис телеметрії

Безперервно шле `POST /api/v1/telemetry` з унікальними даними.

**Що відбувається в Cassandra на кожен запит** (4 round-trip'и):

```
Запит прийшов
  ├─ SELECT з devices_by_id          ← "чи існує такий пристрій?"
  ├─ BATCH INSERT:                   ← зберігаємо телеметрію в 2 таблиці
  │     telemetry_by_device          ← для запитів "вся телеметрія пристрою X"
  │     telemetry_by_device_metric   ← для запитів "вся temperature пристрою X"
  ├─ BATCH INSERT:                   ← оновлюємо метадані пристрою
  │     devices_by_id                ← last_seen_at, battery_level
  │     devices_by_user              ← денормалізована копія для списку пристроїв юзера
  └─ SELECT з device_thresholds      ← "чи є пороги для перевірки алертів?"
```

**Round-trip** — один цикл "запит до Cassandra → очікування відповіді → отримання результату". 4 round-trip'и = 4 мережевих звернення до бази.

`metricValue` встановлено 20-25 (всередині порогів min=10, max=35), тому алерти **не** створюються. Ізолюємо чисту вартість запису.

Кожен наступний запит йде на наступний пристрій (round-robin) — розподіляє записи по різних **партиціях** Cassandra.

> **Партиція** — в Cassandra дані групуються по partition key. Для `telemetry_by_device` partition key = `device_id`. Всі записи одного пристрою лежать на одному вузлі. 5 пристроїв = 5 партицій = 5 незалежних "потоків запису".

### 2. `write-with-alerts` — Запис з генерацією алертів

Те саме, що `write-telemetry`, але `metricValue = 42` (вище порогу max=35). Кожен запит **тригерить алерт**.

Додатковий 5-й round-trip:

```
  └─ BATCH INSERT (алерт):
        alerts_by_id                 ← для запиту "дай алерт по ID"
        alerts_by_location           ← для запиту "всі алерти локації X"
        alerts_by_device             ← для запиту "всі алерти пристрою X"
```

Порівняння з `write-telemetry` показує **write amplification** — скільки "коштує" денормалізація алертів у 3 таблиці.

> **Write amplification** — коли один логічний запис (одне показання сенсора) перетворюється на кілька фізичних записів у різні таблиці. У Cassandra це свідомий компроміс: дублюємо дані, щоб потім швидко читати по різних ключах.

### 3. `read-telemetry` — Читання історії телеметрії

Шле `GET /api/v1/devices/{id}/telemetry?limit=100` з JWT токеном.

Cassandra операції (2 round-trip'и):

```
  ├─ SELECT з devices_by_id          ← перевірка що пристрій належить юзеру
  └─ SELECT з telemetry_by_device    ← партиційний скан з LIMIT 100
       WHERE device_id = ?
       ORDER BY recorded_at DESC     ← вже відсортовано clustering key'ем
       LIMIT 100
```

Це найшвидший сценарій, бо: тільки 2 звернення до бази, дані вже відсортовані на диску.

> **Clustering key** — порядок сортування рядків всередині партиції. В `telemetry_by_device` це `(recorded_at DESC, metric_type, telemetry_id)`. Cassandra фізично зберігає рядки в цьому порядку, тому "останні 100 показань" — просто читання перших 100 записів партиції, без сортування на льоту.

### 4. `read-latest` — Останні показники пристрою

Шле `GET /api/v1/devices/{id}/latest`.

Різниця від `read-telemetry`: цей ендпоінт сканує до **1000 рядків** (захардкоджено в коді), а потім **в пам'яті Go** вибирає останнє показання кожного типу метрики (temperature, humidity, тощо).

Повільніше ніж history, бо скан 1000 рядків vs 100 + post-processing в Go.

### 5. `mixed-workload` — Мікс читання/запису

autocannon отримує масив з 5 шаблонів запитів і циклічно їх чергує:

```
requests: [ write, write, write, write, read, write, write, write, write, read, ... ]
```

Пропорція **80% записів / 20% читань** — близько до реального IoT-трафіку, де сенсори постійно шлють дані, а юзери іноді переглядають графіки.

Показує **contention** (конкуренцію) — чи заважають записи читанням. В Cassandra відповідь "ні": записи йдуть у memtable (RAM), читання паралельно сканують SSTable'и (файли на диску).

## Метрики, що збираються

### Req/s (Requests per second) — Пропускна здатність

Скільки запитів сервер обробив за секунду. Головна метрика продуктивності. Рахується як `загальна кількість запитів / тривалість тесту`.

Приклад: `write-telemetry: 1,441 req/s` означає що Go API + Cassandra обробляють 1,441 запит на запис за секунду. З урахуванням 4 CQL операцій на запит — **~5,764 CQL операцій/сек**.

### Latency (Затримка) — Час відповіді

Скільки мілісекунд проходить від відправки запиту до отримання відповіді. Збираються **перцентилі**:

| Перцентиль | Значення | Інтерпретація |
|-----------|----------|---------------|
| **p50** (медіана) | 50% запитів швидше | "Типова" затримка. `p50 = 6ms` → половина запитів за 6мс або менше |
| **p90** | 90% швидше | "Звичайний найгірший випадок". Кожен 10-й запит повільніший |
| **p99** | 99% швидше | Метрика для SLA. Лише 1 з 100 запитів повільніший. `p99 = 10ms` → навіть у поганому випадку затримка < 10мс |
| **p999** | 99.9% швидше | "Хвіст" розподілу. 1 з 1000. Аномальні затримки (GC паузи, compaction) |
| **Avg** | Арифметичне середнє | Менш корисне: кілька повільних запитів "перетягують" середнє |
| **Max** | Найповільніший запит | `Max = 57ms` — один запит потрапив на compaction або GC паузу |

**Чому перцентилі, а не середнє**: якщо 99 запитів відповіли за 5мс, а 1 за 500мс — середнє буде ~10мс, що не відображає реальність. p99 = 500мс — це чесніше.

### Errors — Помилки з'єднання

Кількість запитів, що не отримали HTTP-відповідь взагалі (TCP timeout, connection reset). Має бути **0**.

### Non-2xx — Серверні помилки

Кількість відповідей зі статусом не 200/201 (тобто 400, 404, 500, 503 тощо). Має бути **0** — якщо з'являються, Cassandra або Go API не витримують навантаження.

### Throughput (MB/s)

Мегабайт відповідей за секунду. Менш важлива для API (JSON невеликий), корисна для виявлення мережевих вузьких місць.

## Оркестратор (`run.js`)

Головний скрипт координує весь процес:

1. **Парсить аргументи**: `--scenario write-telemetry` для одного сценарію, або без аргументів — усі 5
2. **Seed** — створює юзера, пристрої, пороги, наповнює телеметрію
3. **Для кожного сценарію**:
   - Warm-up (5с) — прогрів, результати відкидаються
   - Основний запуск (30с) — вимірювання
   - Друк детальної таблиці autocannon
   - Збереження JSON в `bench/results/<scenario>-<timestamp>.json`
4. **Зведена таблиця** — порівняння всіх сценаріїв

### Ключові висновки

| Що вимірюємо | Результат | Висновок |
|---|---|---|
| Запис телеметрії | 1,441 req/s, p99=10ms | Cassandra ефективно обробляє IoT-записи навіть на 1 вузлі |
| Ціна алертів | -21% throughput, +30% p99 | 3 додаткові таблиці на алерт — відчутна ціна денормалізації |
| Читання vs запис | Читання в 1.6x швидше | Очікувано: 2 CQL ops vs 4 |
| Скан 1000 рядків | 1,328 req/s, p99=17ms | Великі партиційні скани помітно дорожчі |
| Мікс навантаження | Затримка = чистий запис | Читання не конфліктує з записами в Cassandra |
| Стабільність | p50-p99 різниця < 5ms | LSM-дерево Cassandra дає передбачувані затримки |

### Спостереження специфічні для Cassandra

1. **Write-optimized модель підтверджена**: 1,400+ записів/сек на одному Docker-вузлі. Записи йдуть спочатку в memtable (RAM), тому швидкі незалежно від обсягу даних — це властивість LSM-дерева (Log-Structured Merge Tree).

2. **Вартість денормалізації вимірювана**: 4x write amplification без алертів (2 таблиці телеметрії + 2 таблиці пристроїв). 7x з алертами (+3 таблиці). Це свідомий компроміс query-driven моделі Cassandra — швидкі читання ціною множинних записів.

3. **Розподіл партицій має значення**: 5 пристроїв = 5 партицій. Бенчмарк з 1 пристроєм показав би гірші числа через contention на одній партиції. В продакшені з тисячами пристроїв розподіл буде ще кращим.

4. **Затримки стабільні**: різниця між p50 і p99 менше 5мс. Детермінований шлях запису Cassandra (memtable → commitlog) уникає стрибків затримки, характерних для B-tree баз під навантаженням запису.

5. **Обмеження одного вузла**: результати не демонструють горизонтальне масштабування Cassandra. З кластером на 3 вузли і RF=3 throughput записів залишився б подібним (записи йдуть на всі репліки паралельно), а throughput читань міг би масштабуватись лінійно.
